== A third matrix axis: plugin versions

The compatibility matrix varies the *Maven version* and holds the components fixed.
Upstream practice raises the mirror image of that question: when a plugin gets a new trunk SNAPSHOT, every project using it is lifted onto that SNAPSHOT and rebuilt, integration tests included.
A matrix that varied the *plugin version* instead would surface those breakages before the wider ecosystem hits them.

=== What the graph already tells us

The published graph holds every POM of the survey, so the blast radius of a plugin change is a query rather than a guess.

[source,cypher]
----
MATCH (pom:Maven:Pom:Xml)-[:USES_PLUGIN]->(pl:Maven:Plugin)-[:IS_ARTIFACT]->(a:Maven:Artifact)
WHERE a.group = 'org.apache.maven.plugins'
RETURN a.name AS plugin, count(DISTINCT pom) AS poms, count(DISTINCT a.version) AS versions
ORDER BY poms DESC
----

Two readings of that table matter.

The blast radius is large:: A new surefire SNAPSHOT touches 960 POMs.
Rebuilding all of them with integration tests is a far bigger job than the 125 cells of the Maven-version matrix, so this axis cannot simply be added to the existing nightly.

The version spread is the real finding:: 27 different surefire versions and 25 compiler versions are in use across the survey.
That spread is itself a source of inconsistent results, independent of any new SNAPSHOT.

=== Does the problem actually occur?

The question was whether a new plugin release breaking a *different* component is frequent enough to justify the machinery.
Partial evidence, from the same store:

* 932 issues across the 112 repositories carry "regression" or "broke" in the title.
* Of those, 95 sit in `apache/maven` alone and also mention a plugin.

Those counts look impressive but do not carry the weight first attributed to them: the titles were counted, not read, and "mentions a plugin" is far from "was broken by a plugin release".

Once the mailing-list search was repaired (see below) the archive gave a sharper answer, and it argues *against* the third axis.
Across 287,000 messages and two decades, the literal phrases "breaks/broke the/our build" appear 41 times on `dev@` and 49 times on `users@` -- and barely at all since 2018 (2018: 1, 2021: 1, 2023: 2, none on `users@`).
The decline most likely reflects the move to GitHub issues rather than a decline in breakage, but even generously read this is not a drumbeat that justifies multiplying the build matrix.

[TIP]
====
The archive did surface a better argument, and it is about latency rather than frequency.
In February 2017 a committer wrote: "Christian Schulte asked me a couple of days ago whether I am able to build Surefire master with Maven master. It was constantly failing for him on his OpenBSD machines."

Plugin master against Maven master, broken for some time, and discovered because one person happened to ask another.
That is the gap a matrix closes -- and the *existing* two axes already cover it.
====

[NOTE]
====
The mailing-list MCP could not confirm the frequency, but the archive can.
Querying its Elasticsearch index (287,000 messages across `maven-dev` and `maven-users`) directly, with the subject field boosted and phrases like "broke the build" weighted, returns exactly the phenomenon -- `r1639526 in maven-project-info-reports breaks the build` (2014), `M206 Regression: Build is broken` (2007), commit threads on the enforcer and shade plugin trunks.
The same question through the MCP returned only the most recent release announcements, whatever the query terms.

So the limitation is the MCP's query construction, not the corpus and not the retrieval method.
That is worth reporting to the mail-mcp project before anyone reaches for a different indexing approach.
====

=== Would vector search help here?

Probably, but not first, and not as a replacement.

The gap BM25 leaves is vocabulary:: A search for "a plugin release broke a downstream component" does not lexically match "r1639526 in maven-project-info-reports breaks the build".
Dense retrieval closes exactly that gap, and hybrid ranking (BM25 and kNN combined through reciprocal rank fusion) is natively available in the Elasticsearch 8.11 already running here -- no new infrastructure.

The cheaper wins come first:: Field boosting, phrase matching and date filters turned an unusable result set into a useful one in a single query, as the note above shows.
The index also carries extracted metadata that no ranking currently exploits: JIRA references, GitHub commit and PR references, vote flags and decision keywords.
Filtering on those is more precise than any similarity score, because it is structured rather than inferred.

=== Open questions before building anything

. Which plugins are worth watching?
  Surefire, compiler and jar cover most of the blast radius; the long tail probably does not earn a nightly.
. Where does it run?
  The existing matrix already saturates a machine for hours, and this axis is an order of magnitude larger.
. What is the trigger?
  A plugin's trunk moving is the obvious signal, and `compat-tick` already has the two-axis machinery to build on.

== Smaller open items

Distributions for the remaining lines:: `maven-dists.txt` covers 4.0.x only.
`core/3.x/maven-3` builds 3.10.0-SNAPSHOT and `core/maven` builds 4.1.0-SNAPSHOT, so both could be added the same way once 4.0.x has earned its keep.

The matrix has no scheduler:: `compat-tick` renders a launchd template but no agent is loaded on either machine, and the last results date from 2026-06-21.
godestorm is the intended home, as a `runner` role.

A plugin bug worth reporting upstream:: `GitHubIssueScannerPlugin.connect()` chains `fromPropertyFile()` and `fromEnvironment()` inside one try block.
A missing `~/.github` therefore aborts before the environment is ever consulted, and the scanner falls back to anonymous access at 60 requests per hour -- which presents as slowness, not as failure.

== Keep base images and pinned dependencies fresh

Pinning stops the `:latest` lottery but starts a slower rot, and this project has now been bitten from both directions.

`compose.yml` pins `yuzutech/kroki:0.32.1` because a plain `:latest` had been serving a build from May 2025 out of the local image cache, and `neo4j:5.26.20-community` is pinned for the same reason.
Nothing refreshes either.

The opposite failure hit mail-mcp on 2026-09-18: its `pyproject.toml` declared `mcp>=0.9.0` with no upper bound, so the first rebuild in months resolved to `mcp` 2.x, where `FastMCP` had been renamed to `MCPServer`.
The container went into a crash loop and the running MCP server was down until the range was bounded to `<2`.

Dependabot handles both shapes -- `docker` for base images, `pip` for Python ranges -- and raises a reviewable pull request rather than changing anything silently.
mail-mcp already has it configured (there are open `dependabot/docker/python-3.14-slim` branches); maven-tools does not, and its images are pinned by hand.

The rule worth adopting: every pin needs a refresh mechanism, and every range needs an upper bound.

== A Maven 3 control run, to tell their bugs from ours

Guillaume Nodet runs https://github.com/gnodet/maven4-testing[a comparable harness] over a broad corpus of Apache repositories on GitHub Actions.
Its shape is strikingly close to ours -- `jdk-overrides.json` answers the same need as our `jdk21-projects.txt`, `maven4-extra-args.json` the same as `extra-mvn-args.txt`, and `create-chunks.sh` parallelises much as `run-compat-matrix` does.

One thing it has that we do not is a control.
Every project is built twice, once with Maven 3.9.9 and once with the Maven 4 under test, and the outcome is labelled `maven3-failed` when the project was already broken and `maven4-failed` only when Maven 3 was green.
A failure is thus attributed automatically, and the 55 `maven4-failed` issues of the 4.0.0-rc-6 run are a set one can actually read.

Our matrix has no such baseline.
The run of 2026-09-21 produced 33 failures that had to be sorted by hand out of the logs, and the classification -- invoker, resolution, surefire, leftover fixtures -- says how a cell broke, never whether Maven 4 is to blame.
A `m3` variant over the same components would answer that question for every cell at the cost of roughly doubling the run time.

Whether that price is worth paying is open.
A cheaper variant would run the control only for cells that failed, which keeps the green path at its current cost and still attributes every failure.

== What the graph could say about the state of the ecosystem

Both questions below are analysis, not tooling, and neither is urgent.
They are recorded because the data to answer them is already in the store: the Maven POM schema gives every component's dependencies, the git plugin gives commit history, and the github-config plugin now adds the workflows.

Which components are ageing?:: Age has several independent signals, and the graph holds them all.
Last commit date and commit frequency come from the git plugin, release cadence from the version sequence in the POMs, and the JDK and plugin baselines from the build configuration.
A component whose newest release predates its newest commit by years, or whose workflows still test only JDK 8, is a different kind of stale from one that simply sees few commits.
The interesting output is not a ranking but a short list of components that the Maven 4 migration is likely to strand.

Which third-party dependencies has the JDK made redundant?:: Much of what the older Maven components depend on predates the standard library catching up.
File and path handling that `java.nio.file` now covers, string and collection helpers now in `java.util`, zip handling now in `java.util.zip`, HTTP now in `java.net.http`.
Maven 4 raises the baseline far enough that some of these could simply be dropped, and plugins migrated to the v4 API are the natural place to look first.
The graph can enumerate the candidates -- every component, its dependencies, and its source and target levels -- but deciding whether a given replacement is safe stays a reading exercise.

== Watch whether a retirement actually completes

A retirement has four steps: the vote, the announcement, renaming and
archiving the repository, and removal from `apache/maven-sources`.
Only the last one takes the component out of our corpus, and nothing connects the four.

Observed on 2026-09-23: Maven Shared IO had been announced as retired on the 19th, its GitHub description already said `(RETIRED)`, and it was still in the manifest and not archived.
`maven-doxia-book-maven-plugin` and `maven-verifier-plugin`, retired earlier, were complete on all four counts.
So the path works; it is just not walked promptly.

The watch only has to bridge the gap between the decision and the completion -- afterwards the component leaves the manifest and falls out of our corpus by itself.
A list of announced retirements with their dates, and a warning when an entry has been open too long, is therefore enough.
Three sources answer it: our own manifest, the GitHub repository state (`archived`, and whether the description says RETIRED), and the mailing list for `[VOTE] Retire` and `[ANN] Retirement`.

The same query answers the more interesting question too: who in the corpus still depends on a component that is being retired.
For `maven-verifier` we know part of the answer already -- Surefire, whose integration tests cannot run under Maven 4 because `Embedded3xLauncher` reflects on `MavenCli.doMain`, which Maven 4 does not have.

== Disk pressure, not the work, drove the nightly runtime

Worth recording because it was measured twice on two machines and misdiagnosed both times.

On godecane in September a build went from 6550 to 1013 seconds and a scan from 18859 to 3212 for identical work, once the stores were excluded from Time Machine and the local snapshots were thinned.
On godestorm on 2026-10-07 the same thing: the build fell from 116 to 20 minutes for the same 37 repositories, and the whole run from about thirteen hours to 3h26.

The mechanism is not the space itself but the change rate multiplied by the snapshot frequency.
A nightly rewrites around 22000 files under the Maven checkout and writes a 3.5 GB store; the net delta is small, but every hourly snapshot has to retain the previous version of all of it.
Measured: 2.2 GB written in 100 minutes, 16 GiB consumed.

The lesson for anything added later: a path whose contents are reproducible and whose change rate is high belongs outside Time Machine from the start, not after it hurts.
`jqassistant/`, the Maven checkouts, `.m2`, `.m2-isolated`, `.github-cache` and the JDK class cache are all excluded now.

== Check the matrix variants for currency

`variants.txt` drifted for weeks without anyone noticing: it still tracked 4.0.0-rc-5 while rc-7 was in vote, carried five columns of a spike that had finished, and had no row for the released 3.10.0.
The cost is paid every night, and the drift is invisible because a stale column still produces green cells.

Three sources would answer it: the SDKman broker API for released lines (already used for the JDKs), the mailing list for `[VOTE] Release` and `[ANN]` so a candidate shows up before it reaches SDKman, and `variants.txt` itself.

Deliberately NOT an automatic pull request.
A variant is a decision, not a version string: `m4-rc6` looked exactly like a stale RC and was in fact the control column that separated "our bump broke it" from "Maven 4 breaks it anyway".
An automaton would have deleted it.
A line in the nightly mail with the row to paste is the right output.
