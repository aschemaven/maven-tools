# Restrict a project to specific matrix variants.
#
#   <project path>   <variant> [<variant> ...]
#
# Without an entry a project runs against every variant, which is the right
# default: a component should be tested on everything we track.
#
# core/3.x/its-3 is the exception. It is the Maven 3.x integration-test suite,
# and its HEAD tracks maven-3.10.x ("Fix IT failures caused by Maven 3.10.0
# stricter validation level"). Running it against the Maven 4 columns is wrong
# three times over:
#
#   * Redundant. Maven 4 ships its own ITs as core/maven/its and
#     core/maven-4.0.x/its, declared as <module>its</module> and built with
#     those projects. The standalone suite (core/its) was emptied in 2025 when
#     the tests moved into core -- it holds nothing but a README now.
#   * Broken. The 3.x harness drives Maven through maven-shared-verifier's
#     Embedded3xLauncher, which calls MavenCli.doMain; Maven 4's entry point is
#     MavenCling. One m4-40x log carries 868 such errors -- harness noise, not
#     a finding about Maven.
#   * Ruinous. The two most expensive cells ever recorded here are 4.x x its-3:
#     51159s (14.2h) and 9849s. Together about 17h of every full matrix pass,
#     spent on the above.
#
# Against the 3.x columns the suite is expected to be GREEN on every one of
# them, m3-9 included. A red cell there is to be investigated, not explained
# away as suite-versus-version drift: that was the earlier reading of m3-9, and
# it was wrong. The 2026-10-07 m3-9 red was
#   Failed to clean project: Failed to delete .../core-it-suite/target/surefire-reports
# which is the signature of two matrix runs building the same directory. It
# finished at 17:16, and the lock that serialises runs (da4696e) landed the
# next morning at 09:03 -- so the cell is an artifact of the unserialised
# window, not a finding. Same for the m3-10 cell of that window, which claimed
# 0.661s for a suite that needs ~20 minutes. Both were dropped so the table
# shows "no result yet" until they are rebuilt.
#
# The cost objection does not apply to the 3.x columns: the two ruinous cells
# quoted above were Maven 4 ones. The measured worst case for a 3.x run is
# 2790s (46 min), so all three columns together are roughly two hours.
core/3.x/its-3   m3-9 m3-10 m3-10x

# The two mvnd checkouts are the same case as the "-4" lines below, by the same
# criterion -- what the project's own POM declares it is built against:
#
#   core/3.x/mvnd-1  branch mvnd-1.x, <maven.version>3.9.16</maven.version>
#   core/mvnd        branch master,   <maven.version>4.0.0-rc-7</maven.version>
#
# So each belongs to one Maven line, and the opposite columns measure nothing.
# That matches the cells: mvnd-1 is ok on all three 3.x columns and red on all
# three 4.x ones, core/mvnd the reverse.
#
# NOTE for future candidates: "red on every column of one major" is NOT by
# itself a reason to restrict a project. doxia/doxia, plexus/components/compiler,
# maven-ear-plugin and maven-artifact-plugin show exactly that shape, and for
# them the red IS the finding -- a plugin compiled against the Maven 3 API still
# has to run under Maven 4, and ear-plugin/plexus-compiler are the two projects
# where the LRM-split fix was validated 5/5 and 12/0, so their 4.x reds are
# stale pre-fix cells. Restrict only on a declared maven.version, as here.
core/3.x/mvnd-1  m3-9 m3-10 m3-10x
core/mvnd        m4-rc7 m4-40x m4-41x
